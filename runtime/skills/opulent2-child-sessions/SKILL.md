name: opulent2-child-sessions
description: Delegate bounded legal work to actual VM-backed children and consume completed native returns.
---

Use `subagent_create` directly or discover `subagent.create` inside `execute`. Create and start together with `tasks: [{title, prompt}]` and `start: {machine: "fresh"}`. Each child gets a separate VM with the same complete read-only corpus, public task materials, approved tool policy and current scoped memory/Drive. It does not share your writable files or conversation. Include the narrow question, source paths or identities, relevant scenario facts, output expectations and limitations in the assignment. Do not pass hidden rubric information or unsupported conclusions as facts.

For this evaluation the lead must start a useful child, and that child must delegate one narrower question to a real grandchild. This is not an instruction to recurse indefinitely. Grandchildren finish their bounded assignment without having to spawn again. Continue independent work while agents run.

The creation response contains actual child identities and start outcomes. Inspect it; a draft, rejected start, queued ID or provisioned VM is not completed research. Discover and use `subagent.get`, `subagent.events` and `subagent.list` for actual owned-session state. Use `wait` with the returned session operation ID when completion gates you; do not repeatedly poll. The scheduler also delivers child completions. Failed children remain visible and may be diagnosed or explicitly resumed within the task's budgets.

Paths are relative to the calling agent: `2.1` addresses that agent's second child's first child, not a globally numbered agent. A child cannot address its sibling or another root thread. Cross-branch coordination goes through the common parent; an address is not an access grant. Use actual returned session IDs or owned dotted paths, not guessed host thread codes. This runtime does not expose hosted peer threads or pull-request ownership services.

Use direct `message_agent` with no `to` to report to the parent, including `state: "final"` and actual findings. A `working` report with no `to` records progress locally and does not send findings to the parent. A `needs_you` parent report must state the actual decision, access or credential needed; it is not a completed assignment. Inside `execute`, `message.agent` requires a recipient and cannot be used as a terminal parent report. An addressed send steers a descendant and never answers your own parent. A person-facing `message_user` delivery is a separate audience and is not a substitute for the parent-facing work product.

A final report ends the current turn, but real outstanding descendants and durable waits can still keep the assignment pending. Read the actual settled status and final returned work; do not equate a provisional report or wake event with completed research. A stopped branch and its descendants remain parked despite completion events. Resume one selected agent explicitly by message or start; its stopped descendants remain stopped until individually resumed. Read every creation/start outcome and refusal before relying on the batch.

Return source identities, exact decisive quotations, qualifications and unresolved questions, not merely a file path that exists only on the child's VM. The lead reads the returned work, checks decisive sources and integrates or rejects it with reasons. A completion injection is a callback: act on its findings rather than sending an acknowledgment or narrating each child's progress. Neither tool counts nor receiving a completion event establishes meaningful use.
