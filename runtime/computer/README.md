# Prepared E2B desktop image

`build-template.py` creates a separate, credential-free amd64 Ubuntu 24.04 template. It installs the desktop packages, Chrome, Python 3.12's venv, `modal-computer-use==2.0.2`, and the exact vendored source from this directory at build time. It does **not** start the daemon, write an auth token, or include a browser profile. Build-time network and root access are required; evaluation-time bootstrap needs neither.

```sh
/home/user/.capy/work/harvey-eval/repo/.venv/bin/python runtime/computer/build-template.py --alias lux-legal-desktop-amd64-20260927
```

The builder emits a template ID, build ID, image-manifest SHA-256, and vendored-source SHA-256. E2B reused the template ID when rebuilding the same alias, so **neither the alias nor the ID alone proves immutable content**. Record the ID and specific build ID, manifest digest/content, source revision, and Chrome/Python/package versions observed in a sandbox for provenance; do not rebuild that alias for a fixed run. The script uses the host's `E2B_API_KEY` solely to call the build API, never copies it into the image, and leaves the Harvey template untouched.

The default `--profile minimal` preserves the historical build recipe and marker. For the separate, broader public-tools experiment, use `--profile opulent-full-tools --alias <new-unique-alias>`. Its `opulent-full-tools.json` and `opulent-full-tools-requirements.txt` list build-time apt and pip recipes. The expanded schema-1 marker also hashes both recipe files, the builder, and the two supplied inventory files, while retaining the same bootstrap compatibility fields. Record the actual build ID and resolved `pip freeze`/`dpkg-query` outputs: requirements intentionally resolve Python-3.12-compatible public versions at build time rather than claiming the user's Ubuntu 22.04/Python 3.10 versions. The dedicated `/opt/opulent-tools/venv` inherits Ubuntu's `python3-apt`, `python3-gi`, and `python3-dbus`. E2B command sessions override Docker's `ENV PATH`, so the recipe uses a real `.pth` site path for default `/usr/bin/python3` imports and symlinks the venv's genuine generated CLI scripts into `/usr/local/bin`, rather than trusting an image PATH that the command runner discards. Python interpreter symlinks are deliberately excluded because they would escape virtualenv detection. The original `/opt/computer-use/venv` remains independent for the daemon. Build with network and root access, but never install at eval runtime.

The expanded manifest is an availability recipe, not a promise of exact executable parity: shell builtins are resolved by the shell; version-specific Python 3.10/GCC 11 or proprietary/session-specific names cannot be relabeled as Python 3.12 or replaced by no-op shims. Installed Docker/system utilities do not grant daemon access or privileges. Compare both inventories inside the newly built sandbox using `type` and `importlib.metadata`/imports, and report missing names, versions, and failures separately. Keep the existing nonroot, no-new-privileges, credential-free image, read-only corpus, and eval network policy unchanged.

Public CLIs outside the user's 134-distribution Python inventory are separate: pinned `uv`/`poetry` go into an isolated CLI venv, pinned `corepack` is installed with npm, and official amd64 Scala CLI/Coursier/sbt/Scalafmt/Ammonite releases are fetched and SHA-256 verified at build time. Their pinned URLs and upstream-published digests live in `opulent-full-tools.json`; no launchers download dependencies at evaluation time merely to satisfy a command check. A present client may still require project-specific dependencies or an authorized network connection to perform work. The `coursier` name points to the genuine `cs` CLI binary; the sbt archive supplies its own real `sbtn` client.

The expanded profile also installs a real, side-by-side CPython 3.10.20 with uv, retaining Ubuntu 3.12 as default, plus pinned upstream Rust Analyzer/Rustup and the public ngrok/frpc client binaries. Client presence does not supply tunnel authentication or override denied outbound traffic. `bootctl` and `resolvectl` come from SHA-verified Noble `.deb` payloads matched to the installed systemd library version; extracting only their genuine binaries avoids installing bootloader or resolver services into the sandbox. No boot, daemon or network-tunnel operation is run as an availability probe. Version-specific scripts not shipped by these distributions remain missing rather than being relabeled from newer ones.

After a successful build, `audit-template.py --template <template-id> --image-sha256 <image_sha256> --packages <all_python_packages.txt> --utilities <all_utilities.txt> --output <private-audit.json>` probes a real secure, outbound-denied sandbox, imports all 135 mapped modules from the 134 requested distributions using default `python3`, checks the independent desktop SDK, and writes actual versions, resolved apt/pip inventories and command types. The direct network probe records returned HTTP bytes (or their absence), rather than mistaking a successful TCP handshake for permitted egress. It never invokes privileged or destructive utilities merely to count them. The image still needs the existing `createComputer(...).bootstrap()` live check to verify the daemon, browser, and runtime policy.

To prepare the separately versioned six-skill image, add `--skills-dir runtime/skills --alias <new-unique-alias>` to the expanded build after that source tree is final. The builder requires exactly six named directories with nonempty `SKILL.md`, accepts only regular files (plus root `README.md` and an optional `manifest-v1.json` whose declared skill hashes must match), and embeds only relative paths, names and SHA-256 digests in the expanded image marker. It copies the complete archive as root to `/opt/opulent/skills`, then makes every file 0444 and directory 0555 before switching to `user`. Neither the historical minimal template nor the already built v4 image is modified. A parent and newly provisioned child sandbox must each read all six absolute `SKILL.md` paths and match the recorded hashes before they can claim that the skill bundle is available.

To use the prepared path, provision a sandbox from that recorded template ID and call `createComputer(sandbox, { computerPreparedImage: true, computerImageSha256: '<build output image_sha256>' }).bootstrap()` once per new sandbox. The adapter validates the root-owned image manifest against the expected digest, checks its package/bridge compatibility, writes `/tmp/computer-use/bridge.py`, generates a new mode-0600 token in the VM, and starts the loopback daemon as the unprivileged sandbox user. Subsequent attaches call `ready()`; never snapshot a running daemon as a reusable base image, since a snapshot can preserve the per-VM token/profile. Keep the existing sandbox's `secure`/network policy and the broad evaluation's nonroot `setpriv --no-new-privs` command wrapper. `computerPreparedImage` alone does not select an image; the provisioner must select the ID explicitly. A missing or unexpected image fails bootstrap instead of falling back to privileged installation.

The original non-prepared bootstrap remains available for other callers; the broad adapter must opt into the prepared path itself. The daemon's localhost bearer authentication, per-VM token, and existing repository approval policy are unchanged. The prepared image is infrastructure availability, not a graded evaluation or a claim about corpus/provider connectivity.

On the prepared image the daemon starts the lean Openbox manager and Chrome with software rendering and first-run prompts disabled. Without software rendering the daemon reported a launched PID but Chrome did not render a window in the E2B VM. The local browser-console bridge checks the focused window's `WM_CLASS` with `xprop` before allowing CDP evaluation.

## Hardened readiness probe

`probePreparedComputer(sandbox, config, { bootstrap = true } = {})`, exported from `index.mjs`, returns `{ computer, readiness, screenshot }`. Call it after the sandbox command/file protections are applied, with `computerPreparedImage: true` and the approved `computerImageSha256`. It rejects root or missing `NoNewPrivs`, verifies the nonwritable root-owned image marker and adapter compatibility, starts or validates the authenticated loopback daemon, checks the daemon's actual UID/no-new-privileges state, and captures a bounded inline PNG. `bootstrap: false` is validation-only for reconnects; it never installs dependencies, writes a token, or starts a replacement daemon. Prepared bootstraps on the same sandbox handle are single-flight; a later bootstrap validates the existing daemon without regenerating its session token.

The `readiness` descriptor has `schemaVersion: 'e2b-desktop-v1'`, `status: 'ready'`, the prepared-image digest, UID/no-new-privileges fields, daemon privilege fields, and screenshot dimensions/bytes. It reports Linux desktop observation as `screenshot` with `desktopTreeCoverage: 'none'`, and browser observation as `dom-snapshot-v1`. Its `verified` fields attest only the authenticated daemon and desktop screenshot; browser tree/action verification and `nativeModelVision` remain unverified. Approved browser origins are configuration, not a connectivity or action proof. The probe does not navigate, click, upload, alter browser flags, or exercise a model. Keep its raw `screenshot` separate from provenance metadata; publish the descriptor, not image bytes inside a readiness declaration.

Probe errors throw with `code: 'PreparedDesktopUnavailable'` and `stage`: `configuration`, `hardening`, `prepared-bootstrap`, `prepared-ready`, `daemon-hardening`, or `desktop-screenshot`. The caller owns cleanup and readiness/adoption reporting. Do not convert a failed readiness check into package installation or weaken sandbox protections. Model-driven desktop/browser use, native provider image understanding and scored adoption each require their own evidence.
