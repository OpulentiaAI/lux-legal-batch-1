# Opulent2 fixed — native staged experiment v1

This is a new experiment, not an edit or replacement of any historical baseline. Both answerers are RunAnywhere-native `mimo-v2.6-pro` (`xiaomi/mimo-v2.6-pro` logical model), with 1000 steps and 32768 completion tokens per call. Opulent2's native compactor uses 8192 tokens; its calls and all descendant calls count in accounting. No Gateway answerer fallback, inferred price, fabricated provider response, reliability score or turn penalty is permitted.

## Stages and state

1. Run Opulent2 on **task-02, then task-05**. The first starts empty. The second receives the first execution-valid task's actual cumulative model-written memory and local Drive export. Each attempt uses a new private runtime directory and fresh owned VMs. A failed attempt preserves its evidence but never advances state; retry starts from the unchanged accepted predecessor. “Execution-valid” is not a legal grade.
2. The parent reviews both saved work products and the actual delegated assignments/findings, desktop observations, approximate search and persisted/read-back artifacts. Only a parent acceptance binding both results can unlock holdout freezing. Neither the runner nor a capability count decides legal correctness or meaningful usefulness. **Do not select, author or freeze the five holdouts before this acceptance.**
3. After acceptance, select or author exactly five previously unused tasks. Freeze their public task/material bytes and separate hidden rubric hashes against a parent-confirmed complete usage history. Used IDs, public-task hashes and content fingerprints prevent reuse, including renamed copies. The freeze binds the accepted second proving snapshot. A new comparison release and separate authorization are required.
4. Run a fresh five-task matched comparison. Opulent2 continues the same successful memory/Drive chain, sequentially; Harvey starts each task fresh under its intended unchanged source prompt/tools and public-task-v2 adaptation. The two arms run concurrently. No earlier Harvey output, Opulent output, host personal memory, reviewer feedback, grades or hidden criteria enter an answerer's input. Completed arms in this new run never rerun on resume.

State transfer uses the actual `runtime/opulent2-handoff.mjs` API, not launcher-defined memory semantics. The canonical snapshot's `.sha256`, chain ID, parent hash, sequence, tasks, ownership and artifact origins are verified. The full current memory and Drive file contents are appended once to the next root user input using a pinned 32 MiB inline limit. Local SQLite plus explicit JSON export/import is not a connected cloud Drive. Only successful acknowledged model-authored effects are eligible; raw mount edits, transcripts, grading material and credentials are not state seeding.

## Instructions and capability evidence

`runtime/instructions/opulent2-fixed-v1.md`, trimmed at its end, is the exact parent-supplied appendix. It is in the Opulent2 system and each root user request; bounded children receive the exact source role override. It requires useful root → child → grandchild work and actual native results returned to and observed by both parents, a relevant computer inspection, genuine agrep, memory_save/readback and intentional Drive save/readback. Deeper useful work is not artificially prohibited; grandchildren have no obligation to recurse. Harvey receives no Opulent2 appendix or additional behavioral requirements.

Before transmission, the runner pins source-built expected receipts privately. It independently checks the configured adapter prompt and core-assembled prompt/codemode hashes, reconstructs the exact root/child role/schema system plus actual materialized memory indexes, and checks the root user against the frozen public request, verbatim appendix and actual carry-forward assembly. Native transport must then equal the exact prepared system/user/tool definitions. The retained wire and runtime ledgers are rechecked after completion; source text or configuration alone is not transmission evidence.

New reference-integrated releases separately bind the operational reference addendum and the exact once-only approved skill registry in every answerer system assembly. The registry is derived from the same configured inventory used by skill discovery and reads, with artifact hashes and adaptation/exclusion provenance; it is not proof of installed files or a connected provider. The current prepared image and actual installed skill bytes must be verified separately. Historical foundation, task appendix and skill bytes remain pinned rather than replaced by an entire host skill volume. Parent reports, user deliveries and lifecycle notices remain distinct; provisional sleeping-child reports are not completed findings, and stopped branches retain notifications without automatic resumption.

Each root and descendant's registered, dispatcher-allowed and initially visible grants are retained. Actual native assistant responses, factory-owned distinct VM IDs, child completion messages actually transmitted to parents, successful capability returns, real images actually transmitted to the answerer, and exported/read-back contents establish execution. Unprinted execute results, queued child IDs, unseen overflow files and blank-success receipts cannot establish observations. A real agrep no-match is a valid completed search, not fabricated source consultation. The parent reviews whether the actual task work and desktop inspection were useful.

Capability omissions, failed wiring, missing observations or cleanup/accounting defects are **execution failures to diagnose, repair and retry**, not legal-score penalties or invented successes. Failed and interrupted attempts remain visible. Fixing source or policy requires a new release/run identity; changed source cannot be smuggled into a resumed run.

Active Opulent2 VMs retain the configured one-hour renewable lease, with real owned-ID renewals at half-window intervals and bounded cancellable requests. Renewal covers active tools and native inference, preserves immutable command deadlines, and stops before pause, termination or runtime release. A failed renewal is not explicit user cancellation and cannot justify silently replacing lost backing files. Provenance binds the lease policy and implementation; final root status is checked after quiescence and collection. Live lease continuity and native chat health are separate from mocked lifecycle tests and from legal quality.

## Release, accounting and grading

The release pins the final clean source commit and source-file hashes; exact model/catalogue, budgets, corpus/retrieval, prompts/appendix, tool schemas/dispatcher grants, state API/policy/snapshot, task set, protocol, Harvey sources, prepared VM image and replay/evidence policy. A separate parent authorization binds the release's **file-byte hash**, stage and run ID. Drafts and offline tests cannot authorize live calls. A changed release, source, authorization, initial state or policy rejects resume. Output files live only in the new private launch scratch.

The copied native capture/reconciliation and owned-VM infrastructure derives from the read-only `native-capy-v1-launch` modules: native `cbf7c3e0522c3a75721ff91bf8c7fc6775c4874b9d66ca5653bf6a6443b476e6`, cleanup `920b5e7144d80e718a0bc51d976ad1bfa6afaabdde082b0e259ca3d4d845b88a`, IO `a540b1a2280dff3df20c678b0ba2d8c59a9ecd33859e606c4ca5c4fd52bafa4e`. Its internal historical adapter names are lineage, not the experiment's user-facing name.

All native request bytes are hashed before sanitization; private gzip artifacts retain sanitized requests, full/non-2xx/invalid/partial responses, status, actual response IDs, per-call budgets, phases, message/schema sizes, retries and observed usage. Credentials, authorization headers and authenticated URLs are never saved. Successful accounting joins actual response IDs to prepared requests, usage events and provider records, including descendants and compaction. Full consumption/cost stays null when usage or provider prices are unknown; observed subtotals are labeled separately. The observation-only Harvey Python wrapper leaves its upstream loop, tools, prompts, native retry logic and VM settings intact.

Only factory-returned IDs belong to this run. Cleanup operates on those IDs alone; a fresh authenticated query must return the SDK's real typed not-found error. Kill success, arbitrary 404s, account-wide listing and inferred absence do not suffice. Cleanup must complete even when execution fails and before a retry or progression.

Grading is a later parent-owned Jev/Capy step on saved outputs, frozen hidden criteria and actual answerer-visible evidence. This runner does not grade, launch judge inference, change criteria/denominators or claim an uplift. Semantic quality, completed-run performance/cost and failed-attempt/unknown-usage audit are reported separately. Missing providers, credentials and skipped live tests remain explicit.
