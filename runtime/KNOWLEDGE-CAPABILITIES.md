# Knowledge-work capability profile

This is an explicit, separately measured profile, not a new default or a claim of blanket Capy parity. The historical `standalone-v1` runtime, closed-corpus `legal-eval.mjs` policy, and prior evaluation outputs remain available unchanged. `opulent-knowledge-v3` selects knowledge-work instructions, the 64/8 script limits and saved trajectory pass-through in the complex-v1 comparison; its approved initial-scripted inventory, native corpus/MCP setup and dispatcher policy remain unchanged. Registering a tool does not authorize or connect it. See [evaluation protocol](../eval/complex-v1/KNOWLEDGE-RUN-PLAN.md).

## Explicit runtime configuration

For a **direct runtime** with approved local browser access and direct-child waits, select both versioned capabilities and permit their names explicitly. When `initialTools` narrows direct model visibility, add these names there too if direct calls are intended; otherwise a permitted script-callable tool may be discoverable through `scripted_tools`. This example is not a command to widen an existing benchmark policy:

```js
const config = {
  stateDir: '/absolute/path/to/persistent-state',
  runtimeCapabilities: ['browser-v1', 'operation-waits-v1'],
  browserAllowedOrigins: ['http://127.0.0.1:3000'],
  browserUploadRoots: ['/home/user/workspace/approved-uploads'], // only if upload is needed
  maxScriptToolCalls: 64,
  maxConcurrentScriptToolCalls: 8,
  allowedTools: ['scripted_tools', 'browser', 'wait_for_operations'], // add other approved tools intentionally
  initialTools: ['scripted_tools', 'browser', 'wait_for_operations'],
};
```

`runtimeCapabilities` accepts only `browser-v1` and `operation-waits-v1` (without duplicates); omitted means neither extra definition is registered. The extensions do not edit `catalog.json`, `allowedTools`, `initialTools`, or the E2B network configuration automatically. The browser requires a prepared desktop/Chromium and an explicit nonempty origin list. If browser origin controls must be the only network path, do not grant the same model unrestricted shell or `browser_console`; E2B private ingress (`allowPublicTraffic: false`) is **not** outbound denial. A broader corpus/MCP experiment additionally needs `corpusWorkspace`, approved server configuration, credentials and explicit `allowedTools` for its actual adapters; see [eval policy](../eval/README.md). Browser and wait contracts are tested through separately scoped `createRuntime` probes; the complex-v1 **legal pilot intentionally does not enable them or expand its allowlists**. This is a scope choice, not a missing integration gate for that pilot.

## What the portable interfaces do

| Surface | Contract and limits |
| --- | --- |
| Machine file search | `find_file_by_name({pattern,path})` provides filename/relative-path glob matching; `grep({pattern,path,glob_pattern,...})` provides regex content search through the sandbox Python file handler. The real `rg` binary is invoked through `exec`, not a fabricated ripgrep response or a separate tool named `rg`. The file handlers reject paths that escape the workspace, including symlinks. These tools are permitted by the native evaluation allowlist; deferred tools remain discoverable through the runtime/script catalog. |
| Child agents | `opulent_session_create` starts actual child-session workers; `sidekick` is another child interface. Children inherit the evaluation policy and receive separate E2B sandboxes. `opulent_session_interact` and `read_subagent` expose their status and returned output. Creation alone is not completion, and child-only source reads do not become parent evidence unless returned to and read by the parent. Repository allowlists and workflow approvals remain enforced. Delegation is available, not mandatory on every legal task. |
| Python `scripted_tools` | Fresh Python process per call, local `opulent_tools` discovery/description and scoped authenticated broker; static call-site analysis, local basic schema checks, then authoritative server validation, canonical permissions and approvals. The knowledge profile sets **64 nested calls and 8 in flight per program** (`maxScriptToolCalls`, `maxConcurrentScriptToolCalls`). The persistent `script_runs`/`script_calls` ledger assigns a run and ordered call IDs, stores bounded/redacted arguments/results (large entries truncate with a hash), and marks interrupted in-flight calls `uncertain`. Earlier effects are not rolled back; inspect the ledger before retrying. These are not model-turn or transaction limits. Other profiles retain their prior behavior unless limits are explicitly configured. |
| Browser worker (`browser-v1`) | A separate Chromium context over the sandbox's CDP connection; 1–30 statically validated actions, sequential execution, stop on failure, ordered `results`, `executed` (including a failed entry), closing `{epoch, tree, ref_count}` observation, tab/URL metadata, and typed `{code, phase, retry}` failures. `snapshot`/`find` create epoch-bound element refs; obtain a fresh observation after a stale/detached ref. Unknown post-dispatch outcomes are not safe to replay. Browser UI actions marked `unverifiable` are input delivery, not semantic success. `fill`, `select`, and `check` read back state. |
| Desktop and images | The existing coordinate-based `computer` batch validates actions before side effects and returns `status: failed`, `phase`, completed action records, partial results and recovery guidance on failure; a failed/unknown action is not a safe replay. It does not create identity-backed native-app handles or a persistent `App`. Browser screenshots are nested PNG results; image extraction delivers bounded, untrusted model-visible image observations separately from text or reports omission. Computer, `view_image`, and generated images use the same count/byte constraints; a screenshot artifact alone does not prove model vision. |
| Durable wait (`operation-waits-v1`) | `wait_for_operations({operations:[{kind:'session'|'workflow',id}], return_when:'any'|'all', duration_seconds})` or `wake_at` releases the caller; a deadline alone is allowed, at most seven days. Only **owned direct-child** sessions/workflows qualify (not arbitrary host operations). Persistent rows and scheduler ticks notify/resume that session with terminal statuses or timeout; a user continuation can cancel its wait. Notification acknowledgement follows an assistant response checkpoint. This is not a durable Python process, global Capy operation subscription, or platform PR/Slack callback. |
| Dispatch recovery | Schedule occurrences get stable due-time keys; signed webhook deliveries get receipt IDs and payload hashes. Reconciliation inspects tagged child sessions before determining an accepted dispatch. Incomplete or ambiguous dispatches can become `uncertain` and require operator inspection via authenticated `GET /dispatch-recovery`, then an explicit noted acknowledgement via `POST /dispatch-recovery`. Do not blindly redeliver/replay; **exactly-once external effects are not promised**. Use a persistent SQLite store and **single-server ownership per database** for reconciliation; this is not a distributed multi-server lease. |

Browser action fields are deliberately narrower than a generic browser API; the validator in [`browser-tools.mjs`](browser-tools.mjs) is authoritative:

| Action | Accepted fields besides `action` |
| --- | --- |
| `snapshot`, `find`, `navigate` | `interactive?`; `text`; `url`, `new_tab?`, respectively |
| `tab` | `operation: list|new|close|select`, with `id` only for `select`, `url?` only for `new` |
| `click`, `hover`, `fill`, `type`, `select`, `check`, `scroll`, `upload` | `ref`, `epoch`; plus `value` for fill, `text` for type, `values` for select, `checked` for check, `direction: up|down` for scroll, `paths` for upload |
| `key`, `read`, `screenshot`, `console`, `network` | `keys`; none; `full_page?`; `operation: read|clear`; none, respectively |
| `wait`, `dialog`, `viewport` | `until: load|domcontentloaded|networkidle|text`, `text?` only with text, `timeout_ms?`; `operation: accept|dismiss`, `prompt_text?` only with accept; `width`, `height`, respectively |

Requests, subresources and WebSockets are checked against exact approved HTTP(S) origins in the isolated context. **Every HTTP redirect is refused, including approved-origin redirects**, before Chromium follows it; Playwright routing alone does not re-intercept every redirect hop. URL credentials, sensitive query keys, metadata/internal control ports and non-HTTP(S) navigation are refused. Uploads require workspace-confined approved roots, symlink-safe staging and size limits. They do not imply a download API. DNS rebinding is not solved merely by an origin string; use operator-controlled hosts and broker egress policy. Network/console observations omit or redact sensitive fields on a best-effort basis; page text and pixels can still contain sensitive material. **Unsupported:** drag, download artifacts, coordinate browser actions, regex find, screenshot clipping/highlighting, DOM diff, arbitrary JavaScript execution, response bodies/headers and full Capy browser parity. Consult [browser details](browser/README.md) before adding an action; do not silently substitute a different tool.

The standalone runtime intentionally does not carry persistent JavaScript bindings, machine-resident app handles, a native MCP process pool, or Capy's host control plane. Its Python process, direct children, and operator-approved MCP client lifecycle are different interfaces. Capy tasks, threads, paired devices, cross-machine transfer, Drive, setup, platform PR watches and other platform-only services are **not portable baseline requirements**. Preserve authentication, repository allowlists, human approvals, workflow script-hash approval, secret handling and the excluded blueprint, voice, wiki, repository-Q&A, user-management and settings families.
