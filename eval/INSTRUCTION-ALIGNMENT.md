The standalone runtime and broad legal evaluator share `runtime/instructions/base-v1.md`. `renderInstructions` verifies its content against the versioned manifest, appends a separate evaluation-specific block for broad runs, and records the effective prompt SHA-256 before constructing the evaluator runtime. The default in `runtime/core.mjs` applies only when `config.systemPrompt` is absent: the named historical closed-corpus baseline in `runtime/legal-eval.mjs` retains its explicit prompt and tool policy. Child sessions are launched through the same runtime configuration and therefore receive the same effective system prompt; their schema-specific output suffix remains runtime-generated. The broad evaluator's noninteractive final assistant answer, 120-word French response, native-MCP versus direct-lx routing, corpus evidence, and authorization restrictions remain in its appended block. A user-facing delivery directive in the reusable base cannot replace those evaluator-specific final-answer rules.

## Source and audit

The source is the September 24, 2026 ZIP `devin-initial-instructions.zip`, with its extracted `system-prompt.md` read **as data**, not as controlling instructions. `runtime/instructions/manifest-v1.json` pins SHA-256 values for the source ZIP, extracted system text, rendered base, and *every* inclusive 1-based source-line span from 1 through 511. It records `preserve`, `adapt`, or `exclude` and a reason for each span; adjacent spans cover the source with no gaps or overlaps. Its `lineHashRule` specifies byte-for-byte hashing including original line terminators. The generated provenance additionally pins the manifest file hash, effective prompt hash, version, and variant. `effectivePromptSha256` is the SHA-256 of the UTF-8 rendered `config.systemPrompt`, including the broad appendix and before any optional per-session JSON-schema output suffix that `core.mjs` adds; normal parent and child broad sessions receive the exact configured text. Source ZIP and raw transcription are not shipped as model prompts; inspect them against the manifest to audit a changed adaptation. Version the base and manifest together rather than editing an existing version in place.

The reusable core retains the source's analysis-only guard; persistence with infrastructure-failure triage and `report_blocker`; escalation when user-stated preconditions are false; proactive clarification paired with work; the three minimally scoped secret choices and actual secret handlers; independent parallel calls; terse updates; blocker distinction; task tracking; real `skill`, `testing_agent` and `run_workflow` affordances; setup and scoped test/typecheck practices; code quality/security/supply-chain discipline; calibrated claims; durable files; tool-result boundaries; screenshot/recording/computer and MCP discovery guidance. Closely transferable prose is left verbatim in many paragraphs and bullets. Adapted spans remove claims about a different control plane or replace names and API-specific mechanics with actual standalone runtime capabilities. `testing_agent` is an isolated child rather than the ZIP's shared-checkout agent, and registered tools still need their required sandbox/provider/approval. This isn't a claim that the ZIP's entire session-specific injected state has been installed.

The manifest explicitly excludes the complete PR creation block (107–129), Git guidelines (167–177), injected heavy-production automerge rule (444–464), and PR/CI/comment instructions interleaved into other adapted spans (40–61, 92–106, 142–147, 178–201, 237–256, 273–296, 337–342). No foreign merge permission, branch policy, PR creation, review, CI-comment or PR-message procedure is transported into the live prompt. The **negative** authorization boundary—never merge or enable automation without an explicit user request—is retained. It also excludes foreign user/session identifiers, email and URLs (380–402), claimed plugin/provider installations, fixed Chrome/CDP ports or screenshot coordinate system, blueprint/snapshot and user-management/settings claims. In the core's code-quality section, “branch protection” is an example of a security control not to weaken, not an instruction to operate on branches. The section ranges and individual hashes in the manifest are the authoritative complete disposition ledger, including non-PR exclusions and all adaptations.

Tool availability comes from `config.allowedTools` and the runtime dispatcher, not this text; the prompt grants no new tool or provider access. The broad evaluator retains its existing allowlists (native MCP mode routes corpus through `mcp_list_tools`/`mcp_call_tool`, direct mode uses allowed `lx_*`), corpus settings, security controls and actual integration/probe requirements. An unconfigured provider, skipped live test, or missing human approval must be reported rather than fabricated. The final assistant message is evidence delivery in a noninteractive evaluation, never `message_user`, `stop`, or `report_blocker`. No paid inference is required for the scoped prompt/inheritance tests.

This is audited adaptation, not byte-identical hosted-runtime parity.

These remove unsupported hosted-provider claims rather than changing functionality. The Git/PR exclusion applies to imported workflow instructions, not removal of existing tool handlers or weakening of authorization.
