## Parent-authorized live command

```sh
LX_RETRIEVAL_PROFILE=voyage node ./eval/opulent2-fixed/runner.mjs --launch \
  /home/user/.capy/work/opulent2-fixed-launch/proving.release.json \
  /home/user/.capy/work/opulent2-fixed-launch/proving.authorization.json
```

The launch command first authenticates the pinned native catalogue and runs the actual broad adapter preflight, which **does create tracked VMs and call retrieval/desktop tooling** but no answerer model. It then executes task-02 → task-05 natively, with exact native wire capture, actual runtime snapshots, exported state and typed owned-VM cleanup. Required environment variable names are checked without saving values: `RUNA_CLOUD_KEY`, `E2B_API_KEY`, `TURBOPUFFER_API_KEY`, `TURBOPUFFER_REGION`, `AI_GATEWAY_API_KEY`. Missing credentials/providers remain visible; there is no fallback or authentication bypass.

On failure, repair the actual defect and rerun the same launch command only if source/policy are unchanged. It preserves successful outputs and retries only unfinished work from the same predecessor snapshot; it does not spin on broken capabilities. A code, instruction, task, grant, state-policy or snapshot change needs a new release/run/output. No failed attempt advances the chain or gets a legal penalty. Inspect `attempts/*/execution-failure.json`, captured requests/responses and the actual snapshot, not merely aggregate tool counts.

When the adapter returns a result, `unvalidated-result.json` preserves its sanitized output before post-run verification. A failure receipt references that candidate for diagnosis; it is not an execution-success receipt, cannot advance the chain and is not eligible for comparison grading.

The Opulent2 lead checks acknowledged Drive readbacks before accepting either a plain final answer or a final report. A read inside codemode followed by a head/tail, length or hash return is not a full-content observation. Missing observations produce a source-pinned, metadata-only correction in the same session so the model can return and inspect the actual content without restarting the task. This transport check is not a legal-quality judgment and does not replace post-run verification or substantive parent acceptance.

Opulent2 summary repair keeps the same complete input, two-attempt limit, hard character limit and native token budget, but requests a shorter preferred length after the first rejection. A complete repair may exceed the preferred length while remaining within the original hard limit; truncated or otherwise invalid repairs are never accepted. After two locally invalid summaries, Opulent2 can instead persist the exact earlier coherent text history to a real VM file and continue with a metadata-only recovery notice, the original system and initial task, the latest user message and recent complete groups. A tool-produced image or wake notification cannot replace the original assignment. Bounded, scrubbed descriptions from this session's owned task records are separately retained as untrusted model-authored progress claims; they do not establish source consultation or completion. The answerer must actually reopen the needed history, decisive sources and saved artifacts. Pending pixels still follow the separate image transport and observation rules, rather than becoming text-file observations. Recovery retains rejected/prior usage and validates its own prefix, session and policy-bound checkpoint before reuse. Missing backing, an unbounded continuation or transport/abort failures remain explicit failures; historical profiles retain their previous behavior.

Execute retains the unchanged 256,000-character persistent-binding bound. Large transient results belong in block-local bindings, and assigning a saved binding to `undefined` releases its large value. A binding-persistence failure remains a failure, but does not erase a successfully evaluated plain-data return or undo completed effects. Its bounded diagnostics identify large bindings by name and serialized size without exposing their values. The Opulent2 schema explains this distinction so callers do not mistake persistence overflow for result overflow and replay completed mutations.

The fixed profile establishes its pixel-aware text reservation and policy fingerprint before the first image arrives. Introducing pixels therefore does not invalidate an otherwise reusable text summary and restart summarization of the old prefix. Actual image-policy changes still invalidate checkpoints; image byte/count limits, pending-pixel transport, completed-request receipts and the original text/token budgets remain enforced.

The opt-in `opulent2-file-backed-result-budget-v2` delivery policy is selected with `opulent2ResultDeliveryPolicy` in the draft spec and frozen harness options; no arbitrary policy object or budget is admitted. It spills automatic Opulent2 text results above 8,192 serialized characters to complete scrubbed, owned VM files. Previews retain the existing head/tail policy, at most 4,096 characters and less when JSON escaping would exceed the result envelope. Explicit `read`, `skill_read`, `drive_read` and `subagent_get` selections keep the original 64,000-character allowance so source, instruction, findings and recovery readbacks remain fully accessible. Aggregate codemode returns use the automatic threshold, while nested calls use their tool-specific allowance; explicit persistence budgets reach the backing adapter rather than producing an unrecoverable truncated prefix. Explicit smaller context-backing budgets remain supported. Unselected Opulent2 and historical profiles keep their 64,000-character default. Runtime, prepared-request and harness provenance record the effective delivery policy; source, release and context fingerprints prevent policy-crossing resume. Complete-file hashes, source access, pending pixel transport, required full readbacks, frozen grading and model/request/token budgets are unchanged. This policy does not establish full-task latency or legal improvement.

The separately opt-in `opulent2-history-first-continuation-v1` policy is selected with `opulent2ContextContinuationPolicy` in the broad constructor, draft spec and frozen harness options. At a text-context boundary it uses the existing complete, owned, hash-verified VM history backing before requesting any model summary. Its checkpoint records `planned_history_backing`, not summary failure, rejected usage or an attempted summary. The exact system, original assignment, latest user, coherent recent groups and bounded untrusted owned-task progress claims remain in the continuation; older details and opaque provider continuity remain in the original transcript and verified backing for explicit reopening. A reference is not consultation. Missing, inconsistent or incompatible backing fails visibly without inference. Pending pixels and recent native reasoning use the unchanged pixel-aware path. The default remains summary-first, including the original repair/fallback behavior and metadata-free v2 checkpoints; historical profiles cannot select the new policy. All numerical bounds, result-delivery options, permissions and approvals remain unchanged. Effective provenance, source fingerprints and checkpoints bind the policy, and comparison preparation rejects successful state from a different continuation policy. Synthetic offline checks are not live acceptance or a latency claim; parent source integration and separate live authorization remain required.

The summary contract preserves alternatives, conditions and uncertainty; the lead must still reopen decisive sources after compaction. Mandatory nesting stops at the grandchild even if an assignment repeats it, and the post-draft delegated review belongs only to the lead rather than recursively to every reviewer.

Opulent2's summary-only evidence view replaces known OpenAI encrypted reasoning payloads with explicit opaque markers, hashes and lengths, and excludes Gateway routing/billing metadata from assistant messages before summary batching. It preserves plaintext reasoning, unknown reasoning formats, other provider metadata, complete tool calls/results and user text. Original transcripts, exact prefix digests and recent answerer messages retain their original provider fields; this is not a change to native answerer reasoning continuity or evidence observation. The view is version-bound in summary provenance, invalidates incompatible checkpoints and retains the existing character/token bounds, repair attempts, compaction trigger and transport-failure behavior. Historical profiles retain their original summary inputs. Offline replay or smaller summary inputs do not establish native latency improvement.

Opulent2 renews each active owned VM's unchanged one-hour lease at half-window intervals through the real E2B timeout API, including during native answerer and compaction calls. Renewal is serialized and bounded; conservative expiry advances only after acknowledgement. Resource renewal never extends a command's original deadline or changes model, step, token, request or execute budgets. Pause/kill refresh the collection window, then stop and drain renewal before releasing the VM; resumed work attaches to the same owned ID with a new lease controller. Renewal failure remains an infrastructure failure, never a silent replacement VM. Final acceptance rereads the root's settled state rather than trusting an earlier completion receipt. The effective policy and helper source hash are included in provenance. Offline tests do not establish live E2B continuity or native provider health.

The additional supplied runtime, streaming, in-page and parallelism references inform source-verified execution repairs, not a port of unrelated Capy services. Concurrent first execute calls share one executor and retain both persistent bindings. Portable-browser bootstrap archives actual dependency contents rather than a pnpm link. Browser trees escape page-controlled line breaks, admit only displayed refs, and disclose node, field and text omissions without enlarging their limits; desktop DOM observations likewise disclose bounded coverage. Unknown browser mutations still stop without automatic replay. The Captain/MagicPath archive is an offline UI/transcript reference, not backend implementation or current execution evidence.

Process records are scrubbed before persistence, and first-terminal settlement emits one completion notification without allowing a later cancellation or reader failure to overwrite the result. A launch acknowledgement or output-stream failure without exit evidence remains an explicitly uncertain, owned running operation, so it cannot complete a durable wait or justify pausing a resident process. Cancellation checks PID, start time and group membership, then verifies group termination rather than using a PID-only SDK fallback. A verified-live overdue identity remains inspectable and cleanup-addressable with its original deadline; that is not proof of completion or an extension of its budget.

Opulent2 keeps parent reports separate from person-facing deliveries. A user-only child delivery creates an explicit lifecycle notice rather than passing its text off as parent findings, and a sleeping child's provisional final is not published as completed work. Stopping parks the entire owned subtree before asynchronous teardown; queued automatic notifications cannot resume it. Explicit descendant messages carry runtime-owned parent/ancestor metadata, and explicit messaging or direct-child start resumes only the selected agent. Hosted peers, external services and host slot caps are not added. Generated tool descriptions/defaults match the actual handlers; structural timeout and wait checks retain the existing numerical limits.

## Evidence and grading boundary

`checkpoint.json` binds the release/authorization/source and retains every attempt. `execution-success.json` points to actual `result.json`, the canonical accepted snapshot and execution validation; broad artifacts include `.opulent2SnapshotArtifact` and `.opulent2HandoffArtifact`. `native-capture-index.json`, `harvey-native-capture-index.json`, `native-model-records.json`, `aggregate-native-accounting.json` and `owned-absence.json` preserve wire, accounting and cleanup. Prices/unknown consumption remain null, not zero. Successful metadata/receipts are not a legal grade.

The parent independently grades the saved work products against the frozen hidden rubrics and actual transmitted/returned evidence after verifying execution. The runner never invokes a judge, changes a rubric, feeds grades back, fabricates capabilities or claims measured improvement. Offline tests are synthetic invariant tests, **not live connectivity, native image understanding or substantive proving-task passes**. See [PROTOCOL.md](PROTOCOL.md) for the complete pinned policy.
