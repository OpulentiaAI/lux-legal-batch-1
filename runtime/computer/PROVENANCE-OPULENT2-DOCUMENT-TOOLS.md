Observed limitations remain visible:

- anydoc correctly refuses scanned PDFs with `needsOcr`; no hosted Firecrawl fallback is enabled. English local OCR supplies the alternative. Additional OCR languages require a new pinned recipe.
- LiteParse's upstream native OCR code downloads from mutable `tessdata_best/main` when a requested language is missing. The prepared `parse` CLI fixes the offline path, rejects arbitrary config/server/language options and removes hosted API environment settings; the bounded runtime adapter must use the explicit prepared English path too. Published `dist/cli.js` gives `batch-parse` no config/tessdata override, so the wrapper rejects it unless `--no-ocr` is explicit. Use `opulent-document` for bounded offline OCR. At pinned source commit `ab8879623ee45a0b7a775d12b42a9a7ae9dab16b`, `crates/liteparse/src/parser.rs` constructor, `is_complex` and `screenshot_input` do not initialize/call an OCR engine; real rendering/complexity fixtures also exercise those prepared commands. Unknown/ambiguous command layouts are rejected rather than inheriting an unreviewed OCR path. Raw upstream APIs are not a network sandbox and retain upstream network-capable features; existing network policy must still apply.
- LiteParse's `--version` banner is hardcoded `2.0.0` in its published `2.15.1` package. The availability report records both, using package integrity/metadata as release identity rather than pretending that banner is accurate.
- rga `--rga-no-cache` fails native preprocessing with `No cache?` in both locally tested `0.10.10` and `0.10.9`. The selected `0.10.10` works with an explicit private `--rga-cache-path=DIR`; the equals-form is required. Pandoc's plain DOCX adapter drops Title-style metadata, so rga is not proof of complete document extraction.
- The inventory's cloud, daemon, desktop-administration, unrelated development utilities and shell tokens are not new document-layer installs. `odfpy` is not selected because its distribution is source-only; anydoc/LibreOffice cover the required OpenDocument work without unpinned build dependencies. Deprecation notices from ExcelJS's locked older transitive npm dependencies remain visible; the four initially observed npm audit findings were fixed with tested exact overrides, not suppressed or replaced with shims.

No E2B template/VM, model inference, provider OCR or scored task was run by this work. The parent owns the eventual uniquely named template build and live readiness/adoption evidence. Local recipe/fixture checks do not authorize comparison resume or prove a live E2B pass.
