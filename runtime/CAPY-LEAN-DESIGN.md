# Capy-derived runtime replacement

Jeremy's 2026-10-04 direction replaces the active mixed-source experiment: reduce the tool surface to relevant Capy capabilities and use a slightly adapted Capy instruction source, retaining full environment and corpus access. It supersedes the proposed additional professional-review/v13 layer, which is not part of this candidate. Historical profiles and their results remain unchanged.

## Product contract

`opulent-capy-v1` uses one supplied Capy instruction capture, with source-span provenance for narrow persona/API adaptations and removal of irrelevant platform/session material. It does not inherit the Prime/Devin foundation or append the historical evaluation instruction stack. A short environment appendix states the real public-input, read-only corpus and output locations. Source text does not grant unavailable services, credentials or permissions.

The active capabilities cover shell and files, safe patches, code execution, task/dependency tracking, session inspection and messaging, hierarchical agent spawning, durable waits/operation control, relevant skills, scoped persistent memory and corpus research. Relevant existing machine browser/computer access can be discovered when available. Full schemas are obtained on demand through the compact codemode interface instead of placing the entire historical catalog in every request. Definitions, discovery and dispatcher authorization use the same explicit policy. Unrelated deployments, review platforms, administration, external image services and other unused integrations are excluded.

Hierarchical delegation retains real independently provisioned child VMs, owned descendant addressing and inherited corpus/security policy. No new depth or fan-out quota is introduced. A child ID is not completed work; real results must be collected. The parent verifies consequential evidence without mandatory RLM capture/read/decide/finish ceremonies. Large results remain retrievable in complete file-backed form; only the content actually returned to the model earns consultation credit.

Memory is a real local-runtime persistent capability, not a claim of Capy cloud Drive. Trusted configuration determines owner/project scopes and durable backing; topic files and their index materialize into the VM with safe atomic updates. Restart/reconnect persistence, scope isolation, traversal/symlink protections and credential handling must be tested. A fresh experiment never imports saved benchmark answers or prior task-specific memories.

The execution lane supports actual isolated JS/TS codemode, persistent plain-data bindings, top-level await/return, exact schema lookup and safe calls into the same dispatcher. It must not expose the host filesystem, network, environment or credentials. Partial effects survive a failed program and are reported honestly; retrying a program must not silently repeat completed effects. Unsupported source-platform features remain explicit rather than simulated.

Communication is a real runtime control, not a prompt-only convention. `message_user` records working updates without ending the model loop, completes with actual nonempty output on `final`, and blocks with the actual request on `needs_you`. A parent's assigned output schema applies to a child's terminal report. Neither an opener nor an attachment path substitutes for a required work product. Work-item dependencies remain separate from child-agent sessions.

## Resource correction

The preserved five-task v9 successful-attempt comparison contains 1,403 unique successful Opulent inference responses versus 213 for Harvey. Opulent used 256,591,427 input and 1,821,093 output tokens; Harvey used 11,144,644 input and 418,205 output tokens. No context-compaction event occurred in those Opulent trajectories, and a single request reached 628,558 input tokens. The complete histories repeatedly carry tool output and handoff bookkeeping; 606 handoff receipts were issued.

The later v12 task-03 request bodies directly show 103 full tool schemas (169,955 encoded bytes) on every answerer request, alongside 215,344–217,346 bytes of system instructions. Those byte counts are not token-cost estimates and are not asserted to be byte-identical historical v9 captures. The one-source prompt and compact tool surface remove fixed overhead; bounded context preparation addresses growing transcript replay. Complete original traces and source files remain available outside the model summary. Compaction uses the same native model, labels summaries as derived context and records every actual summary request and its usage.

Compaction limits must accommodate coherent parallel tool-call groups and recent results together. A parent-side synthetic reproduction against the original compactor showed that the provisional 300,000-character input budget, 160,000-character summary-input budget and six retained groups fail on both three parallel 60,000-character results and seven successive 60,000-character reads. Those provisional settings are not a verified release configuration. The replacement must test these cases without splitting call/result pairs or silently dropping history; synthetic token fixtures are not provider usage measurements.

Preserve the original task, rubric, native RunAnywhere MiMo model, output-token/step budgets, Voyage corpus version and successful Harvey outputs. New policies, prompts, implementation hashes and context settings receive new checkpoint/output bindings; they never resume old runs.

Report measured prompt/tool payload size, actual successful and failed-call usage, compaction costs, successful-attempt latency, completion and independently graded output quality separately. Unknown failed-request consumption and native monetary cost remain unknown. Synthetic tests prove implementation behavior, not a live performance gain. No favorable score or resource reduction is claimed until the native replacement has run and its delivered work has been checked.
