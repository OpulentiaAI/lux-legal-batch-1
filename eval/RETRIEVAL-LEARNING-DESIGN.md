# Offline retrieval diagnostics and reviewed knowledge boundary

`eval/retrieval-diagnostics.mjs` is a read-only consumer of an existing comparison checkpoint and its **evidence-v4 judge-only replay**. It emits *issue candidates*, never fixes, legal conclusions, or accepted knowledge. It does not call a provider, inspect gold/rubrics, mutate the corpus, tune embeddings, or write to production.

```sh
node eval/retrieval-diagnostics.mjs \
  --comparison /absolute/outside-repo/comparison.json \
  --rejudge /absolute/outside-repo/rejudged-v4.json \
  --output /absolute/outside-repo/retrieval-issues.json
```

All paths must be absolute and outside the repository; existing outputs, symlink paths, nonregular inputs, and oversized inputs are refused. The output is newly created with mode `0600`, outside the repository. The CLI checks recorded metadata: replay's original question/corpus provenance and exact comparison input hash, **complete matching row key sets** (no subset replay), unchanged answer for judged rows, per-row proof binding, and source inventory fields. A replay row that omits an unavailable harness answer is skipped only when its original row, failure stage, error, `original_row_sha256`, and replay unavailable inventory agree exactly. The replay should already have been produced by `eval/rejudge.mjs --evidence-v4` with its artifact/source verification. This diagnostic is **metadata-bound only**: it does **not** reread or hash the original artifacts/corpus, verify transport authenticity, or independently authenticate source text. It cannot establish that an arbitrary fabricated JSON pair came from a real run. No raw questions, source excerpts, judge prose, tool output, secret values, or corpus files appear in the output; it carries source/record hashes, ID, kind, origin coordinates and scope. `artifact_hashes_sha256` hashes the replay's *claimed* artifact-hash inventory, and `artifact_name_digest` hashes an origin filename, **not its contents**. Inspect the replay artifact and original evidence separately for actual per-file hashes.

Each item records `status: candidate`, a stage, source-hashed evidence, alternative hypotheses and the next verification action. Current recorded inputs support these bounded observations:

- `retrieved_but_not_hydrated`: a cited ID appears in the comparison's sanitized `audit.calls[].result.ids`, but neither source inventory includes it. The audit is ID-only; verify the actual tool result before treating it as a search hit with missing full text.
- `visible_but_omitted_by_extraction`: a cited ID appears in the historical comparison source inventory but not the stricter replay-visible source inventory. The historical inventory could have used a weaker visibility rule; inspect the replay artifact before changing extraction.
- `citation_mismatch`: a cited ID lacks replay-visible text, or `citation_ok:false` despite cited IDs being visible. This can be answer attribution, content support, validator semantics or an unobserved retrieval path; it is **not** a finding that the cited legal claim is false.
- `judge_error`: a rejudge row explicitly failed at the judge stage. A judge error is not a retrieval or legal-answer failure. `unknown` remains available for a historical source inventory with no citation and no replay-visible source.

There is deliberately **no automatic `never_retrieved` verdict**. The comparison's sanitized audit ID arrays are not a complete search universe (especially for `bash`, `exec`, scripted or MCP wrappers), and even a complete top-k list would establish only a miss at that cutoff. To make this distinction, capture the exact model-visible query/filter, namespace/profile, complete ranked top-k IDs and result status per call, plus hydration attempts, under a separately versioned evidence policy. Then compare against verified source identity and state explicitly “not in recorded top-k,” rather than “not in corpus.” A lack of traces stays unknown. A model-visible preview may be an excerpt, not a full hydrated source. `source.origin` and `kind` from replay preserve that distinction.

## Investigation procedure

For a candidate, inspect the hash-bound original search/output and replay origin; compare the same query with and without inferred filters, BM25/vector/fusion/rerank ranks, hydration output, and source chunk/version. Establish a matched baseline of successful queries and plausible alternative causes. Only then propose a targeted ingestion/filter/ranking/extraction fix and test it on development cases, with fresh held-out questions and stable corpus/profile/model/evidence policy. Preserve historical closed-corpus runs as a separate named baseline. A score difference after changing the judge, sources, or policy is not a retrieval gain. Never tune to frozen benchmark answers.

## Typed legal knowledge, later and separate

The nine-document graph in `type/lx.document.type.yaml`, `type/lx.structure.type.yaml`, `type/lx.article.type.yaml`, `type/lx.chunk.type.yaml` is source structure; it is not a reviewed claim register. Future `knowledge_candidate` records should carry an atomic claim, claim type (statute/secondary interpretation/definition), exact source `doc_id`/`chunk_id` and quoted span hash, full chunk hash, edition/consolidation date, authority, Luxembourg jurisdiction, applicable company form, and *source-supported* effective interval (otherwise unknown). An agent answer, reference snippet, judge analysis, and unverified outside page may suggest an investigation but can never serve as legal authority.

An **independent** reviewer rehydrates the source and checks exact entailment, exceptions, authority, temporal/form scope and prior claims; malformed or missing verdicts reject. A qualified human approves any proposition made available for legal answering. Acceptance appends an immutable event binding the unchanged candidate digest, source/version digest, reviewer decision, human approval and scope; never edit an accepted record in place. Exact duplicates are rejected, compatible corroboration links source records, supersession appends a dated edge only with supporting authority, and unresolved conflicts are quarantined within their overlapping jurisdiction/form/date scope. A later consolidation does not erase historical law and a treatise does not override a statute. Rejected and disputed records remain non-retrievable audit entries.

Only if a consumer is shown to need this register should a read-only, scope-filtered lookup be added separately from the chunk index; it must return source IDs and authority labels, and answers must cite the hydrated source. Do not embed paraphrases into the existing turbopuffer chunks or expose the lookup to the historical three-tool baseline. For a named expanded eval, `eval/README.md` requires both model-visible tool definitions and dispatcher `config.allowedTools`, source-visible evidence capture, and checkpoint provenance for the register/corpus snapshot, tool policy, model/budgets and evidence/scoring version. This document and diagnostic perform **no production writes** and propose no provider change.
